接口需要返回金额、报表需要保留两位小数时，我通常先区分两个问题：是在处理一个数值，还是在生成最终给人看的文字？`round()` 和 `sprintf()` 看起来都能“保留两位小数”，解决的问题却不一样。

这篇笔记从两段输出不同的代码说起，记录浮点表示、显示格式和业务舍入规则之间的关系。

## 一、为什么同样是 .455，结果却不同？

```php
var_dump(sprintf('%.2f', 123.455));
var_dump(sprintf('%.2f', 12.455));
var_dump(round(12.235, 2));
```

在常见的双精度浮点环境、使用小数点的区域设置下，可能看到：

```text
string(6) "123.45"
string(5) "12.46"
float(12.24)
```

PHP 的 `float` 通常采用 IEEE 754 双精度格式。许多十进制小数没有精确的有限二进制表示，因此保存的是附近的一个可表示值。在这个例子中，`123.455` 的实际保存值略小于书写的十进制值，`12.455` 则略大于它。

可以多打印几位，观察这种差别：

```php
printf("%.17F\n", 123.455);
printf("%.17F\n", 12.455);
```

典型输出：

```text
123.45499999999999829
12.45500000000000007
```

当数值恰好处在舍入边界附近时，这一点误差就可能影响最后一位。源码里都写着 `.455`，不代表内部存储的小数部分完全相同。

排查时最好一起记录 `PHP_VERSION`、区域设置和输入值。上面的输出是理解问题的例子，不应当作为所有平台和 PHP 版本的固定承诺。原理可以参考 [PHP 浮点数说明](https://www.php.net/manual/en/language.types.float.php)。

## 二、sprintf() 负责展示格式

```php
$result = sprintf('%.2f', 12.455);

var_dump($result);                 // string(5) "12.46"，典型环境下
var_dump(sprintf('%.2f', 12));     // string(5) "12.00"
```

`%.2f` 要求输出两位小数，返回的是字符串，末尾的零也会保留。它适合报表、页面文字等最终展示环节。

小写 `%f` 受区域设置影响。如果程序输出要求始终使用英文句点作为小数分隔符，可以改用大写 `%F`：

```php
$result = sprintf('%.2F', 12.455);
```

这里处理的是格式，输入仍然是已经存在表示误差的 `float`。把它格式化成字符串，并不等于恢复了最初精确的十进制数值。格式定义见 [sprintf 官方文档](https://www.php.net/manual/en/function.sprintf.php)。

## 三、round() 负责数值舍入

```php
$result = round(12.235, 2);

var_dump($result);       // float(12.24)
var_dump(round(12, 2));  // float(12)
```

`round()` 返回 `float`，可以继续参与运算，但不保证展示出固定的小数位。`12` 与 `12.00` 在数值上相等，显示成什么样，应交给输出层决定。

| 要求 | 常见选择 | 返回类型 |
| --- | --- | --- |
| 页面始终显示两位小数 | `sprintf('%.2F', $value)` | `string` |
| 按指定规则舍入后继续运算 | `round($value, 2, $mode)` | `float` |
| 精确保存、计算十进制金额 | 整数最小货币单位或 BCMath | 按方案确定 |

`round()` 不会把后续运算变成精确的十进制运算，也不宜据此推断它和 `sprintf()` 在所有临界输入上必然输出相同的结果。

### 明确业务需要的舍入方式

下面四种常量都可以显式指定规则：

```php
round(12.235, 2, PHP_ROUND_HALF_UP);
round(12.235, 2, PHP_ROUND_HALF_DOWN);
round(12.235, 2, PHP_ROUND_HALF_EVEN);
round(12.235, 2, PHP_ROUND_HALF_ODD);
```

它们主要区别在于恰好位于中点时如何处理。用能被二进制精确表示的 `2.5` 和 `3.5` 更容易观察：

| 规则 | `2.5` 舍入到整数 | `3.5` 舍入到整数 | 中点处理 |
| --- | --- | --- | --- |
| `PHP_ROUND_HALF_UP` | 3 | 4 | 远离零 |
| `PHP_ROUND_HALF_DOWN` | 2 | 3 | 靠近零 |
| `PHP_ROUND_HALF_EVEN` | 2 | 4 | 取相邻偶数 |
| `PHP_ROUND_HALF_ODD` | 3 | 3 | 取相邻奇数 |

负数尤其容易读错：`round(-2.5, 0, PHP_ROUND_HALF_UP)` 的结果是 `-3.0`，不是 `-2.0`。这里的 UP 指中点时远离零。

PHP 8.4 还提供了 `RoundingMode` 枚举及更多模式；上面的常量写法可用于较早版本。默认规则、版本变化和完整示例见 [round 官方文档](https://www.php.net/manual/en/function.round.php)。

## 四、金额计算从输入阶段就要选对表示方式

假设订单需要记录 12.34 元，在确定币种最小单位为“分”的前提下，可以保存整数 `1234`。多笔订单相加时先加整数，展示时再转换成元，并考虑整数溢出、折扣和税费的舍入规则。

不要先写 `12.34 * 100`，再假定计算过程已经摆脱浮点误差。更稳妥的入口是规范化的十进制字符串，或上游直接传入整数分；解析时校验小数位数、范围和币种。

如果使用 BCMath，参数也应从一开始就是十进制字符串。例如安装 BCMath 扩展后：

```php
$total = bcadd('12.34', '0.10', 2);
var_dump($total); // string(5) "12.44"
```

BCMath 的精度参数不应直接当成业务上的四舍五入规则；发生除法、折扣分摊或超出指定小数位时，还要明确截断、舍入和尾差分配方式。相关接口见 [bcadd 官方文档](https://www.php.net/manual/en/function.bcadd.php)。

做金额功能时，我会把“如何保存”“何时舍入”“如何展示”分别约定清楚，再用边界值验证。这样能避免一段展示代码无意中承担了结算规则。
